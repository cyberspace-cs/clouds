# Hackathon Rapid Build

黑客松全流程作战手册。适用于 24-72 小时的黑客马拉松/AI 黑客松/创新大赛。

## 时间分配原则

标准 48 小时黑客松的推荐时间分配：

| 阶段 | 占比 | 时间 | 目标 |
| --- | --- | --- | --- |
| 选题 + 规划 | 20% | ~10h | 确定做什么、不做什么 |
| 核心功能 | 50% | ~24h | 跑通主流程 demo |
| Demo 打磨 | 20% | ~10h | 去掉日志、假数据、一键演示 |
| Buffer | 10% | ~4h | 集成坑、部署 drama、墨菲定律 |

## 阶段 1：选题筛选（前 4 小时）

### 评委视角筛选框架

用这个框架快速评估每个 idea：

1. **Problem 清晰度**：一句话说清痛点是什么？
2. **Demo 可行性**：48 小时内能跑通主流程吗？
3. **技术亮点**：有没有一个"wow"的技术点？
4. **故事性**：能不能讲出一个打动人的故事？
5. **差异化**：和现有方案有什么本质不同？

### 决策规则

- 如果有超过 3 个 idea 纠结 → 选「技术最酷 + 最快出 demo」的那个
- 如果只有 1 个 idea → 立刻进入 MVP 定义，不要再发散
- 如果团队有人强烈反对 → 听他的，因为他是最可能掉链子的那个

## 阶段 2：MVP 定义（前 6 小时）

### MoSCoW 范围切分

| 优先级 | 定义 | 例子 |
| --- | --- | --- |
| **Must have** | 没它就不是这个项目 | 核心 AI 功能能跑通 |
| **Should have** | 重要但可砍 | 用户登录、基本 UI |
| **Could have** | 锦上添花 | 暗色模式、分享功能 |
| **Won't have** | 明确不做 | 移动端适配、支付 |

### MVP 验收标准

MVP 完成的标志：
- [ ] 一个核心用户场景端到端跑通
- [ ] 至少一个真实工作的组件（不是 mock）
- [ ] 能在演示电脑上一键启动

## 阶段 3：快速原型（中间 24 小时）

### Vibe Coding 工作流

核心循环：**Prompt → 生成 → 预览 → 批判 → 迭代**

1. 每次只做一个小模块
2. 生成后立刻预览，不要攒一大堆再看
3. 发现问题立刻改，不要留到最后
4. 中间产物存盘，方便 debug 和解释

### 快速原型技巧

- **前端**：用现成模板（Vite + Tailwind + shadcn/ui），不要从零写 CSS
- **后端**：能 mock 就 mock，能 hardcode 就 hardcode
- **AI 功能**：先写死一个好的示例输出，再接真实 API
- **数据**：准备 3-5 个完美演示用例，不要用真实脏数据

## 阶段 4：Demo 打磨（最后 10 小时）

### Demo 准备清单

- [ ] 去掉所有 console.log / debug 输出
- [ ] 去掉所有"请输入 API key"的提示
- [ ] 准备好 3-5 个完美演示用例（一键点击）
- [ ] 网络断了也能跑（本地缓存/预录视频备用）
- [ ] 演示路径烂熟于心，不要现场探索

### 降级方案

准备 Plan B：
- 如果 AI API 挂了 → 预录好的视频
- 如果部署挂了 → 本地跑 + 录屏
- 如果网络挂了 → 全部本地运行

## 阶段 5：Pitch 答辩（最后 1 小时）

### 3 分钟 Pitch 结构

| 时间 | 内容 | 要点 |
| --- | --- | --- |
| 0-15s | Hook | 一个震撼的问题或数据 |
| 15-45s | Problem | 痛点有多痛？谁在痛？ |
| 45s-2min | Solution + Demo | 我们怎么做的 + 现场演示 |
| 2-2:30 | Why now | 为什么现在做这个？ |
| 2:30-3min | Vision | 未来能变成什么？ |

### Pitch 禁忌

- ❌ 不要念 PPT 上的字
- ❌ 不要说"我们还有很多功能没做完"
- ❌ 不要解释技术细节（评委不关心）
- ❌ 不要超时（会被打断）
